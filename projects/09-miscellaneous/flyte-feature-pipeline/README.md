# Flyte Feature Engineering Pipeline — POC

A proof-of-concept demonstrating Flyte's core orchestration primitives via a customer feature engineering pipeline.

## What this POC covers

| Concept | Where |
|---|---|
| `@task` with `cache=True` | `src/tasks/features.py` — all three feature tasks |
| `cache_version` for invalidation | Same — bump `"1.0"` → `"1.1"` to force recompute |
| Typed I/O (`FlyteFile`, `pd.DataFrame`, `FlyteDirectory`) | All task signatures |
| Parallel task execution | `workflow.py` — agg / temporal / category run concurrently |
| `@workflow` DAG composition | `src/workflow.py` |
| Local execution (no cluster) | `scripts/run_local.py` |

## Pipeline DAG

```
ingest_raw_data  (no cache — I/O is cheap)
        │
        ├──► compute_aggregation_features  ──┐  ← cached
        ├──► compute_temporal_features    ──┤  ← cached (parallel)
        └──► compute_category_features   ──┘  ← cached
                        │
                  merge_features  (join + StandardScaler)
                        │
                 save_feature_store  →  FlyteDirectory (Parquet artifact)
```

## Caching in depth

Flyte hashes each task's **inputs** deterministically. If the hash matches a prior run, the cached output is returned and the task body is skipped entirely — no compute, no wait.

```python
# Flip cache=True on any expensive task
@task(cache=True, cache_version="1.0")
def compute_aggregation_features(df: pd.DataFrame) -> pd.DataFrame:
    ...

# To invalidate cache (e.g. logic changed): bump the version string
@task(cache=True, cache_version="1.1")   # ← forces recompute
```

On a real Flyte cluster (Propeller + datacatalog), cached results are stored in the metadata store and shared across users and runs. Locally, flytekit simulates this within the process.

## Caching: local vs cluster

`cache=True` in the `@task` decorator is real Flyte metadata — but it is **only enforced by the Flyte cluster backend (datacatalog)**, not by local execution.

| Execution mode | Cache behaviour |
|---|---|
| `python scripts/run_local.py` | Task bodies always execute — `cache=True` is metadata only |
| `pyflyte run` (local) | Same — no datacatalog available |
| Full Flyte cluster (`flyte sandbox start`) | On rerun with same inputs → task body **skipped**, cached output returned instantly |

### What the cache key is

Flyte hashes the **serialised inputs** of each task. Same DataFrame bytes → same hash → cache hit. The cache is also scoped to `cache_version`, so bumping `"1.0"` → `"1.1"` forces recomputation even for identical inputs.

### To see real caching in action

```bash
# Start the local Flyte sandbox (requires Docker)
flyte sandbox start

# Register and run — first run computes, second run hits cache
pyflyte run --remote src/workflow.py feature_pipeline --csv_path data/orders.csv
pyflyte run --remote src/workflow.py feature_pipeline --csv_path data/orders.csv
# Second run: feature tasks show status=CACHED in the Flyte UI
```

## Flyte vs Airflow

| | Flyte | Airflow |
|---|---|---|
| **Unit of work** | `@task` — typed Python function | `Operator` — class with execute() |
| **Data passing** | Native typed I/O between tasks | XComs (size-limited, weakly typed) |
| **Caching** | Built-in per-task, keyed on input hash | Not built-in — DIY with sensors/skips |
| **Parallelism** | Tasks in a workflow run concurrently by default | Requires explicit fan-out with Dynamic DAGs |
| **Versioning** | Tasks and workflows are versioned artifacts | DAGs are mutable files |
| **ML/data focus** | First-class: FlyteFile, FlyteDirectory, map tasks | General-purpose — ML support via plugins |
| **Local dev** | `pyflyte run` or plain Python | Full Airflow stack (scheduler + webserver) |
| **Maturity** | Newer, smaller ecosystem | Battle-tested, huge ecosystem |

**When to pick Flyte:** ML/feature pipelines, strong typing matters, you want built-in caching and artifact tracking.

**When to pick Airflow:** General ETL/ELT, team already uses it, integrations with many external systems are needed.
